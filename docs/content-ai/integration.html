Integration walkthrough

Wiring a refine-and-review flow end to end: a contract, a server action that runs the substrate, the useAiSuggestions bridge, and the registry components that render the review UI. The snippets are adapted from the Spicemixer admin (recipe / ingredient / pairing forms).

Three layers, one boundary

An integration is three layers stacked on the seam. The substrate (the npm packages) is headless and I/O-free. The registry components are a copy-in UI layer — installed into your app via the component registry, not an npm dependency — so you own and restyle them. The bridge is your server action: the one place storage, the event log, and the model key live.

1

Author the contract

The contract is the vocabulary both layers share. A Zod schema defines the entity; fields carry per-field systemPrompt (return "" to gate a field off), bulk flags (what a full refresh targets), and translation behavior. Define it once, server-side, and re-export the field-path type so client callsites are typo-checked. 

// src/contracts/recipeContract.ts
import type { AiContract } from "@pixelmord/content-ai-core";
import { recipeSchema } from "@/schemas/recipe.ts";

export const recipeContract = {
  schema: recipeSchema,
  presets: [{ id: "tighten", label: "Tighten copy", userPrompt: "Make it concise." }],
  fields: {
    title:       { bulk: true, systemPrompt: (ctx) => `Improve the recipe title. ${ctx.userPrompt ?? ""}` },
    description: { bulk: true, systemPrompt: () => "Write a one-paragraph description.",
                   translation: { mode: "translate" } },
    // systemPrompt returning "" gates the field off for this run:
    notes:       { systemPrompt: (ctx) => (ctx.preset === "tighten" ? "Trim the notes." : "") },
  },
} satisfies AiContract<typeof recipeSchema>;

// Field-path union → typos at callsites become TS errors.
export type RecipeFieldPath = keyof typeof recipeContract.fields;

See the core guide for the full contract vocabulary.

2

Run the substrate behind a server action

This is the bridge — and the only place I/O happens. The action reads current data and the event log, calls runRefresh (which drives runRefine), persists any auto-applied writes and emitted events in your assemble strategy, then shapes a RunResult for the client. Server-only: createProvider and tracing come from /server. 

// src/actions/ai.ts  (Astro action / route handler — server only)
import { runRefresh } from "@pixelmord/content-ai-refine";
import { recipeContract } from "@/contracts/recipeContract.ts";

export const aiRefreshRecipeSuggestions = defineAction({
  handler: async ({ id, locale, payload, target }) => {
    const result = await runRefresh({
      contract: recipeContract,
      currentData: payload,
      // per-field scope: target exactly these fields, skip side-effect proposers
      ...(target?.length ? { target } : {}),
      config: resolveConfig(),            // provider base URL · key · model
      events: await eventLog.read(entityRef),  // rejection history → suppression
      // assemble is the seam: the ONLY place store + event writes happen.
      strategy: {
        assemble: async ({ suggestions, autoApplied, events }) => {
          for (const ev of events) await eventLog.append(entityRef, ev);
          for (const [field, applied] of autoApplied) await store.write(field, applied.value);
          return { suggestions, autoApplied };
        },
      },
    });

    // Shape into the RunResult the client hook expects (records keyed by field).
    return adaptToRunResult(result);  // { suggestions, autoApplied, traces, fieldSummaries }
  },
});
The runner never writes. If you find yourself reaching for the store or event log anywhere but assemble, the boundary has leaked — see control flow.
3

Bridge to the UI with useAiSuggestions

useAiSuggestions (a registry hook) holds all review state — suggestions, auto-applied values, traces, per-field accessors, the overview roll-up. You feed it the contract and two callbacks: onRefine (prompt-driven, calls your refine action) and onFill (source-driven / translation, calls your fill action). The hook passes params.target for per-field runs. 

// RecipeForm.tsx (client)
import { useAiSuggestions } from "@/components/use-ai-suggestions"; // from the registry
import { actions } from "astro:actions";

const aiFlow = useAiSuggestions({
  contract: recipeContract,
  currentData: formValues,
  entityRef: { kind: "recipe", id },
  aiEventLog,                       // client-side log adapter
  origin: { surface: "admin", action: "refine", entityKind: "recipe",
            userInitiated: true, runId: `recipe-${id}`, triggeredBy: "editor" },

  onRefine: async (params) => {
    const { data } = await actions.aiRefreshRecipeSuggestions({
      id, locale, payload: formValues,
      ...(params.target?.length ? { target: params.target } : {}),
    });
    return data!;                   // RunResult: { suggestions, autoApplied, traces, fieldSummaries }
  },

  // Optional — only if you support source-driven fill / translation:
  onFill: async (params) => {
    const { data, error } = await actions.aiFillTranslation({ /* …source… */ });
    if (error) throw new Error(error.message);
    return data!;
  },
  siblingLocale: siblingLocaleData ?? undefined,  // enables translation accessors
});
4

Render the registry review components

Wrap the form in SuggestionFlowProvider so the components read the flow from context instead of prop-drilling. Then drop them in: a global trigger (AiBulkSuggestButton with overviewFields renders the SuggestionsOverview dropdown), and per-field inline components keyed by fieldPath. Each inline component pulls its accessor via useSuggestionFlowContext().forField(path) — accept/reject calls recordAccept / recordReject, which feed the next run's suppression. 

import {
  SuggestionFlowProvider,
  AiBulkSuggestButton,
  InlineTextSuggestion,
  ConfidenceBadge,
} from "@/components"; // copy-in registry components

const overviewFields = [
  { field: "title",       label: "Title",       anchor: "field-title" },
  { field: "description", label: "Description", anchor: "field-description" },
];

<SuggestionFlowProvider value={aiFlow}>
  {/* Global trigger + "what did the AI change?" overview */}
  <AiBulkSuggestButton overviewFields={overviewFields} />

  {/* Per field — fieldPath is type-checked against RecipeFieldPath */}
  <div id="field-title">
    <label>Title</label>
    <input value={formValues.title} onChange={…} />
    <InlineTextSuggestion
      fieldPath="title"
      currentValue={formValues.title}
      onApply={(value) => setField("title", value)}
    />
  </div>
</SuggestionFlowProvider>

global

AiBulkSuggestButton · SuggestionsOverview

Triggers aiFlow.run() and lists which fields got new suggestions — including the all-duplicate case, so a run is never silently empty.

per field

InlineTextSuggestion + siblings

Inline{Text,Array,Enum,MultiEnum,Date}Suggestion + AiFieldSuggestButton. Pick by field type; all read the same per-field accessor.

signal

ConfidenceBadge · SuggestionTraceInfo

Render the suggestion's self-reported confidence and a trace link. Confidence is an uncalibrated self-report — don't gate destructive actions on it.

source-driven

IngestDialog

The modal for the runFill path — see step 5.

5

Source-driven fill & translation

When content comes from outside the entity — a PDF, image, pasted text, or a sibling-locale entity to translate — the path is runFill behind your fill action, surfaced by the registry IngestDialog. Pass it the same flow (so it can show presets / write-policy and reuse the review UI) and an onRun that triggers the call. Translation always goes through runFill — runRefine rejects sibling-locale sources. 

import { IngestDialog } from "@/components";

<IngestDialog
  open={open}
  onOpenChange={setOpen}
  flow={aiFlow}                       // shares review state with the inline components
  presets={recipeContract.presets}
  onRun={async (source) => {
    // source: { kind: "pdf" | "image" | "text" | "url", … }
    // Hand it to your fill action, which calls runFill server-side with an IngestContract:
    const result = await actions.aiFillRecipe({ source, locale });
    aiFlow.ingestRefresh(result);     // reuse the same review UI as the refine path
  }}
/>

On the server, the fill action mirrors step 2 but calls runFill with an IngestContract; see the ingest guide.

Closing the loop

The two layers meet at the event log. When an editor rejects a suggestion, the inline component's recordReject appends a rejected event; on the next run your action passes those events into the runner, and the substrate suppresses that exact fingerprint. Accepted and auto-applied writes are recorded the same way. Persisting those events is a write — so it lives in your action / assemble, never in the substrate.
